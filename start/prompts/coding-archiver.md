# 编程归档（GPT；我说"结束"时，或编程任务的机器验收全部通过时）

只归档**编程栏**，只改下面列出的文件。给别人看的部分必须精简（预算见 `start/RULES.md` §1）。

## 同步清单
1. `git pull --rebase`，避免覆盖 Muse 刚推送的改动。
2. `journey/coding-log.md` 追加 1 行（≤ 120 字）：`日期 | 用时 | 任务ID | 做了什么 | 机器验收: ✓/✗/未跑 | 卡点`。用时问我，按小时记一位小数（5 分钟记 0.1h），说不出就写"未知"；任务 ID 用完整形式（如 `C1-P03`）。
3. `campaign.md` **编程表**中该任务的状态：第一次 → `进行中`；机器验收全部 ✓ → `通过`。
4. `start/STATE.md` **只改"编程"小节**：当前编程任务、上次停在哪、卡点、下一步。
5. 任务通过时：
   - `results/` 中放好代码和测试；代码目录的 README 按 `start/templates/experiment-readme.md` 写（≤ 30 行，结论由我口述，你整理措辞，不替我下结论）
   - 有新结论时，`results/README.md` 结论表（`<!-- results:start -->` 与 `<!-- results:end -->` 之间）加一行
   - `journey/README.md` 时间线加一行
   - STATE 指向下一个编程任务；任务卡不存在就在"下一步"写"下次开始时起草"
6. 我在写代码时用自己的话说清楚的理解，写进 `journey/notes/<主题>.md`（≤ 1 页，同主题追加）；没有就不写。
7. 用时检查：本战役编程已用时超过已通过和当前编程任务计划用时之和的 1.5 倍时，在 STATE 编程小节写一行提醒，不替我砍。
8. 运行 `python start/scripts/progress.py` 直到全部 ✓。
9. 分开提交：我写的代码用 `[me] <一句话>`，其余用 `[ai] 编程归档：<任务ID> <一句话>`；推送前再 `git pull --rebase`，首页进度块冲突时重新运行 progress.py 生成。
10. 用 2–3 行告诉我：改了什么、进度条现在是多少、下次从哪里开始。

## 写作规则
- 数字从工具输出原样复制，不编造；不写免责句；新文件用英文短横线命名。
- 不改阅读和动手的文件、不改验收条件、不新建规则或计划。
