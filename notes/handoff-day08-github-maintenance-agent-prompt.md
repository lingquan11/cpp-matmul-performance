## 5. 性能数据真实性规则

本 ZIP 中出现的以下数字均是教学练习中的示例或假设值：

- IPC、CPI、指令数和运行时间的演算；
- LLC 未命中率、MLP；
- 带宽利用率、访问延迟；
- Memory Bound / Core Bound；
- Pipeline Slots；
- A/B/C/D 组因子实验数据和交互项。

这些数字可以留在学习笔记和报告中，用于解释概念，但**不是学习者电脑上的实际测量数据**。

因此：

- 不得把它们写进正式 benchmark CSV；
- 不得创建伪造的原始测量 CSV；
- 不得将理论模型结果标为 chrono 实测；
- 不得把推测的微架构机制写成已经证实的因果关系；
- 若仓库已有 Day 8 原始 CSV，应以真实文件为准，并核对其来源。

## 7. 写入、合并和版本控制流程

1. 先建立清晰的工作分支，命名遵循仓库现有规范；若项目规定直接提交默认分支，则遵循项目政策。
2. 解压并检查 ZIP，不要直接覆盖仓库文件。
3. 按上述映射逐个合并文件。
4. 对现有文件使用最小差异更新；保留历史内容和已有链接。
5. 更新 `PROJECT_STATE.md`。
6. 仅在仓库已有索引规范时，更新根 README 或 notes/reports 索引。
7. 将 GitHub Agent 提示词放到仓库既有的 agent prompt/handoff 位置；不要添加 Day 9 教学交接提示词。
8. 运行检查：
   - `git status --short`
   - `git diff --check`
   - `git diff --stat`
   - `git diff -- PROJECT_STATE.md`
   - 检查新增 Markdown 文件非空；
   - 检查相对链接目标存在；
   - 检查没有教学示例数据进入正式 results 原始数据；
   - 检查没有覆盖 `src/` 中已有最终源码；
   - 检查 ZIP manifest 中每个应入库文件均有处理结果。
9. 如果项目有文档 lint、测试或 CI，按项目规范执行；不要运行与本次文档归档无关、可能破坏数据的脚本。
10. 按项目规范提交变更。建议提交说明可采用：
    `docs(day08): archive performance analysis learning`
11. 是否推送、创建 PR，遵循仓库的权限和工作流；不要绕过保护分支策略。
