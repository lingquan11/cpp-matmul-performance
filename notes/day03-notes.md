## 我怎么理解 O(n³)

我想的是两个 n×n 方阵的朴素三重循环。i 选结果的一行，有 n 个值。i 固定以后，j 选结果的一列，也是 n 个值，所以 i、j 的组合有 n² 个。每一对 i、j 再用 k 走 n 个乘积并累加，得到一个结果元素。

最内层乘积累加的总次数，主要项是 n × n × n = n³。如果一次乘法、一次加法和一次下标访问都按常数成本算，时间复杂度是 O(n³)，也可以写成 Θ(n³)。把结果初始化是 O(n²)，不改变这个阶。

我一开始说成“i 有 n 次，j 有 n 的平方，k 有 n 的三次方”。现在我分得清：每一层自己都是 n 次，n² 和 n³ 是把外层乘进去之后的次数。

边长从 n 变成 2n 时，(2n)³ / n³ = 8。计算量变成原来的 8 倍。我当时说“8到64，正增长8倍”，意思是从 8 变成 64，是原来的 8 倍。这是计算量，不是我已经测到的耗时倍数。实测倍数在 `experiments/reports/2026-10-26-ijk-scale.md`。

## 我当天写的测量方案

我想比较同一段朴素乘法在不同规模下要跑多久。规模用 64×64、128×128、256×256。编译用 Release，并把编译器、版本和实际优化选项记下来，因为光写一个 Release 看不出开了什么优化。环境记下 CPU、操作系统、内存和电源模式，后台尽量别乱动。输入固定、能复现，取值别把我用的整数类型乘溢出。正式测量前先预热，预热不进统计。每种规模正式测 5 次，每次的原始耗时都留着，再算平均。时钟用单调的，比如 C++ 的 steady_clock。计时只包住矩阵乘法本身。分配内存、准备输入、把结果清零、打印和正确性检查都放在计时外面。测量前后我要检查结果，计时结束之后还得用一下这个结果，免得编译器把计算删掉。时间单位统一，相邻规模的平均耗时拿来比，波动留在原始数据里。

如果程序是往 C 里累加的，每次正式测量前我要把 C 清零，不然上一次会污染下一次。单次短到接近计时精度时，我就改成在样本里重复，并把怎么换算记下来。

我之所以不只测一次，是因为后台任务和 CPU 频率会晃。把每次都留下来，我才能看见晃了多少。平均通常比单次更像样，但也不能保证把偏差都消掉。

cout 放在计时外面，是因为打印还有格式化和输出的开销。我想测的是乘法本身。

边长翻倍时计算量变成 8 倍。实际耗时比还会受缓存、编译优化、系统负载和测量误差影响，这个得靠后面的实验看。
