# 实验记录：朴素 i-j-k 矩阵乘法的规模扫描

- 日期：2026-10-26
- 阶段：早期。固定 2×2 的三重循环已经有了，这一次只测量它在不同规模下的耗时。循环重排、分块、脉动阵列都还没有实现。
- 作者：东南大学电子信息大一
- 数据：[`results/2026-10-26_ijk-scale/`](../results/2026-10-26_ijk-scale/)。下面的数字都来自这次运行的 `summary.csv` 和 `raw.csv`，没有另做一次测量来替换它们。

这不是阶段 C 的分块实验报告。阶段 C 还没开始。

## 1. 问题

NPU 和 AI 芯片把大量面积用在乘加和数据搬移上，因为模型里的核心运算是矩阵乘法。教科书上的朴素算法是三重循环，运算次数是 Θ(n³)。运算次数只说明要做多少次乘加，不说明这些数能不能及时从缓存里拿出来。

这份记录要回答一个很小、但是可以核对的问题：把已有的 i-j-k 循环从 n=64 放到 n=1024，耗时是不是大约按运算量变成 8 倍？如果不是，差在哪一个规模。

## 2. 代码里实际有什么

| 文件 | 状态 |
| --- | --- |
| `src/day01_matrix.cpp` | 只算 C[0][0]，不是完整矩阵乘法，不参与计时 |
| `src/day02_matrix.cpp` | 固定 2×2 的 i-j-k。原始输入输出是 `11 10` / `19 30` |
| `benchmarks/kernels/ijk.cpp` | 同一套 i-j-k，上界改成参数 n，供计时调用。2026-10-26 测量时文件还叫 `benchmarks/ijk_kernel.cpp`，循环体没有改，数据没有重跑 |
| 循环重排、分块、脉动阵列 | 计划中，仓库里没有这些文件 |

测量用的循环是：

```text
for i, for j:
  C[i][j] = 0
  for k: C[i][j] += A[i][k] * B[k][j]
```

A、B、C 按行主序存放。B 的相邻两次 k 访问相差 n 个 `int`。

## 3. 方法

正式样本只包含实现函数的连续调用。输入构造、校准和正确性检查在计时外面。`ijk` 在函数内部把 C 的元素写成 0，所以清零算在耗时里。这和 2026-10-25 定的第一版口径一致，和 Day 3 笔记里「清零放在计时外」不是同一次实验。

单次调用如果短于 100 ms，就在同一样本里连续重复。单次耗时 = 样本总耗时 / 重复次数。每个规模 5 个正式样本。表里用中位数。原始的每一次都留在 `raw.csv`。

GFLOPS 的定义是：

```text
GFLOPS = 2 * n^3 / 单次耗时（秒） / 1e9
```

2 表示内层每一次做 1 次乘法和 1 次加法。内核是 32 位整数，不是 float。这个数用来比较同一次实验里的不同规模，不能当成这台 CPU 的浮点算力，也没有去除以峰值。

正确性：基准会先跑 Day 2 原程序，核对输出仍是 `11 10` / `19 30`。参数化后的 `ijk` 还核对了单位矩阵、零矩阵、全 1 矩阵和 n=3 的校验和。同一规模的 5 个样本校验和相同。

## 4. 环境

记录在 [`environment.txt`](../results/2026-10-26_ijk-scale/environment.txt)，测量时刻 2026-10-26T04:05:29Z。

- 机器：KVM 云端 VM，Ubuntu 24.04.5 LTS，Linux 6.12.94+
- CPU：`lscpu` 的型号字符串是 Intel(R) Xeon(R) Processor，family 6，model 207，stepping 2，4 vCPU。没有 cpufreq，所以没有标称频率
- 缓存（`lscpu` 原文）：L1d 192 KiB（4 instances），L1i 128 KiB（4 instances），L2 8 MiB（4 instances），L3 320 MiB（1 instance）
- 内存：MemTotal 16387280 kB
- 编译器：g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0
- 编译命令：`g++ -O2 -std=c++17 -Wall -Wextra -Werror -o build/matmul_bench benchmarks/matmul_bench.cpp benchmarks/ijk_kernel.cpp`
- 没有 `-flto`，没有 `-march=native`，没有 `-falign-loops`，没有绑核，没有采 perf 计数器

之后的 `python3 benchmarks/run_bench.py` 会多一个 `-falign-loops=32`。这是计时工具的选项，不改循环写法。同一天在这台 VM 上做过一次对照：两份循环体相同的函数，只因链接位置不同，n=64 测得大约 3.87 和 6.94 GFLOPS；加上该选项后大约是 6.84 和 6.85（各 2 个样本）。所以上表里的 i-j-k 落在较快的那种布局（6.93），规模之间的比较仍然可用，但不要把以后带这个选项的绝对值和本表混在一起。

`lscpu` 写 4 instances。下面把 L1d、L2 理解成每核一份，也就是每核 L1d 48 KiB、每核 L2 2 MiB，L3 是 320 MiB 共享。这是对字段的读法，不是另一次缓存测量。

三个 `int` 矩阵的总字节数按 4 字节 `int` 估算（结果文件没有单独打印 `sizeof(int)`；x86-64 上的 g++ 里 `int` 是 4 字节）：

| n | 三个矩阵一共 | B 的 k 方向跨步 |
| ---: | ---: | ---: |
| 64 | 48 KiB | 256 B |
| 128 | 192 KiB | 512 B |
| 256 | 768 KiB | 1 KiB |
| 512 | 3 MiB | 2 KiB |
| 1024 | 12 MiB | 4 KiB |

12 MiB 仍然远小于记录里的 320 MiB L3。

## 5. 结果

![i-j-k 三重循环在不同矩阵规模下的耗时与 GFLOPS](../results/2026-10-26_ijk-scale/perf.png)

点是 5 次正式样本的中位数，误差线是同组最小和最大。左图纵轴是毫秒。

| 规模 n | 样本内重复 | 正式样本 | 单次耗时中位数 (ms) | 单次耗时最小–最大 (ms) | GFLOPS | 相对上一档耗时倍数 |
| ---: | ---: | ---: | ---: | --- | ---: | ---: |
| 64 | 1322 | 5 | 0.075661 | 0.075447–0.077330 | 6.929414 | — |
| 128 | 79 | 5 | 1.285246 | 1.283210–1.333168 | 3.263424 | 16.986855 |
| 256 | 8 | 5 | 13.434294 | 13.413632–13.465532 | 2.497670 | 10.452699 |
| 512 | 1 | 5 | 104.810185 | 104.400495–105.745261 | 2.561158 | 7.801689 |
| 1024 | 1 | 5 | 3773.059512 | 3737.205793–3821.183449 | 0.569162 | 35.998978 |

n=1024 的 GFLOPS 是 **0.569162**。n=64 的 6.929414 约为它的 12.17 倍（6.929414 / 0.569162），也就是 n=1024 只有 n=64 的约 8.2%。

n=1024 的五次耗时从 3737.21 ms 到 3821.18 ms，极差约为中位数的 2.2%。36 倍的耗时落差比样本波动大得多，不是某一次被打断造成的。

## 6. 分析

n 翻倍时，按上面的 GFLOPS 定义，乘加次数变成 8 倍。如果每次乘加的平均耗时不变，耗时也应该大约变成 8 倍，GFLOPS 应大致持平。测到的耗时倍数是：

| 规模变化 | 运算量倍数 | 耗时倍数 | 耗时倍数 / 8 |
| --- | ---: | ---: | ---: |
| 64 → 128 | 8 | 16.986855 | 2.12 |
| 128 → 256 | 8 | 10.452699 | 1.31 |
| 256 → 512 | 8 | 7.801689 | 0.98 |
| 512 → 1024 | 8 | 35.998978 | 4.50 |

最后一列就是 GFLOPS 下降的倍数。例如 n=512 的 2.561158 除以 n=1024 的 0.569162，也是约 4.50。数据和定义是对齐的。

由此可以直接说的只有这些：

1. 耗时不跟 n³ 成一个固定比例。GFLOPS 从 n=64 的 6.93 降到 n=1024 的 0.569。
2. 下降不是均匀的。256 → 512 的耗时倍数是 7.80，接近 8，GFLOPS 从 2.498 到 2.561，基本持平。明显的掉速发生在 512 → 1024。
3. 用第 4 节的缓存读法，n=64 的三个矩阵一共 48 KiB，和每核 L1d 同一量级；n=128 和 n=256 放得进每核 2 MiB 的 L2；n=512 的 3 MiB 超过每核 L2，但耗时倍数仍接近 8；n=1024 的 12 MiB 仍在 320 MiB 的 L3 里面。所以这组数据不支持「矩阵放不进 L3，所以 GFLOPS 掉了」。也不支持「工作集一旦超过某一级缓存，耗时就一定偏离 8 倍」——256 → 512 就是反例。

代码里能确定的访问差异是：内层沿 k 走时，B 的地址跨步是 `n` 个 `int`。n=64 时跨步 256 字节，n=1024 时跨步 4096 字节。跨步越大，同样次数的访问越不容易落在同一条缓存行里。

**假设（这次没有测量来证实）：** 512 → 1024 的掉速和 B 的大跨步有关。若页大小是常见的 4 KiB，n=1024 的跨步正好是一页，有可能带上额外的 TLB 压力。结果目录没有页大小，也没有 cache-miss 或 dTLB-miss 计数，所以这只是和数据不矛盾的猜想，不是结论。要检验它，需要在同一口径下看 `perf stat` 一类的计数，或者加上循环重排后再比。

另外，绝对 GFLOPS 最高也只有 6.93。这台机器的 `lscpu` 带有 AVX-512 标志，但本次编译没有 `-march=native`，也没有把整数乘加自动向量化到什么程度写进结果。不能把 6.93 解释成「达到了峰值的百分之几」。

## 7. 局限

- 只有一种实现，图还不是循环顺序或分块的对比。
- 云端 VM，型号字符串是通用的 Xeon，没有固定频率，也没有绑核。数字只在这一次实验内部比较。
- 整数核。GFLOPS 是按乘加次数折算的，不是 IEEE 浮点吞吐。
- 没有 perf 计数器，缓存和 TLB 的解释停在假设。
- n=64 的单次调用只有 0.076 ms，正式样本是 1322 次调用的平均。这是事先写明的换算，不是 1322 个独立的墙钟样本。
- Day 3 的零矩阵输出是当时自报的，这次实验记录没有重跑那个交互过程；基准里的零矩阵检查是参数化内核自己的检查。
