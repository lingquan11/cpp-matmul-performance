# 实验记录：朴素 i-j-k 矩阵乘法的规模扫描

- 日期：2026-10-26
- 阶段：i-j-k 基线的规模扫描
- 作者：东南大学电子信息大一
- 数据：[`results/2026-10-26_ijk-scale/`](../results/2026-10-26_ijk-scale/)，数字来自该目录的 `summary.csv` 和 `raw.csv`

## 1. 问题

NPU 和 AI 芯片把大量面积用在乘加和数据搬移上，因为模型里的核心运算是矩阵乘法。朴素算法是三重循环，运算次数是 Θ(n³)。运算次数给出乘加的总量，数据是否及时到达则要靠测量。

这次扫描回答一个具体问题：i-j-k 从 n=64 放到 n=1024 时，耗时是否大约按运算量变成 8 倍，差别出现在哪一档规模。

## 2. 实现

| 文件 | 内容 |
| --- | --- |
| `src/day01_matrix.cpp` | 计算 C[0][0] |
| `src/day02_matrix.cpp` | 固定 2×2 的 i-j-k，输出 `11 10` / `19 30` |
| `benchmarks/kernels/ijk.cpp` | 同一套 i-j-k，上界为参数 n。2026-10-26 的测量记录里，源文件路径写作 `benchmarks/ijk_kernel.cpp`，现位于 `benchmarks/kernels/ijk.cpp` |

测量用的循环是：

```text
for i, for j:
  C[i][j] = 0
  for k: C[i][j] += A[i][k] * B[k][j]
```

A、B、C 按行主序存放。B 在 k 方向上相邻两次访问相差 n 个 `int`。

循环重排、分块、脉动阵列与 SCALE-Sim 写在第 8 节。

## 3. 方法

正式样本只包含实现函数的连续调用。输入构造、校准和正确性检查在计时外面。`ijk` 在函数内部把 C 的元素写成 0，清零计入耗时。这是 2026-10-25 定下的口径；Day 3 笔记里的方案把清零放在计时外，两套口径的数据分开读。

单次调用短于 100 ms 时，在同一样本里连续重复。单次耗时 = 样本总耗时 / 重复次数。每个规模 5 个正式样本，表中取中位数，每一次原始耗时在 `raw.csv`。

```text
GFLOPS = 2 * n^3 / 单次耗时（秒） / 1e9
```

2 表示内层每一次做 1 次乘法和 1 次加法。内核是 32 位整数。GFLOPS 用于同一次实验里不同规模的比较。

正确性检查包括：Day 2 原程序输出 `11 10` / `19 30`；参数化后的 `ijk` 在单位矩阵、零矩阵、全 1 矩阵和 n=3 上与逐项乘加一致。同一规模的 5 个样本校验和相同。

这次测量的编译命令如上，包含的优化级别是 `-O2`。当前的 `python3 benchmarks/run_bench.py` 另外带有 `-falign-loops=32`，用来让各内核的循环落在相同的对齐边界上。同一天在这台 VM 上用两份相同循环做过对照：n=64、各 2 个样本时，不对齐大约是 3.87 和 6.94 GFLOPS，加上该选项后大约是 6.84 和 6.85。上表的 i-j-k 约为 6.93，与较快的那一档一致。两套编译选项不同，绝对值分开比较。

`lscpu` 的 4 instances 在下面按每核一份来读：每核 L1d 48 KiB，每核 L2 2 MiB，L3 320 MiB 共享。这是对字段的读法。

三个 `int` 矩阵的字节数按 4 字节估算（x86-64 上 g++ 的 `int` 为 4 字节；结果文件未单独打印 `sizeof(int)`）：

| n | 三个矩阵一共 | B 的 k 方向跨步 |
| ---: | ---: | ---: |
| 64 | 48 KiB | 256 B |
| 128 | 192 KiB | 512 B |
| 256 | 768 KiB | 1 KiB |
| 512 | 3 MiB | 2 KiB |
| 1024 | 12 MiB | 4 KiB |

12 MiB 低于记录中的 320 MiB L3。

## 5. 结果

![i-j-k 三重循环在不同矩阵规模下的耗时与 GFLOPS](../results/2026-10-26_ijk-scale/perf.png)

点是 5 次正式样本的中位数，误差线是同组最小和最大。左图纵轴是毫秒。

| 规模 n | 样本内重复 | 正式样本 | 单次耗时中位数 (ms) | 单次耗时最小–最大 (ms) | GFLOPS | 相对上一档耗时倍数 |
| ---: | ---: | ---: | ---: | --- | ---: | ---: |
| 64 | 1322 | 5 | 0.075661 | 0.075447–0.077330 | 6.929414 | — |
| 128 | 79 | 5 | 1.285246 | 1.283210–1.333168 | 3.263424 | 16.986855 |
| 256 | 8 | 5 | 13.434294 | 13.413632–13.465532 | 2.497670 | 10.452699 |
| 512 | 1 | 5 | 104.810185 | 104.400495–105.745261 | 2.561158 | 7.801689 |
| 1024 | 1 | 5 | 3773.059512 | 3737.205793–3821.183449 | 0.569162 | 35.998978 |

n=1024 的 GFLOPS 是 **0.569162**。n=64 的 6.929414 约为它的 12.17 倍（6.929414 / 0.569162），即 n=1024 约为 n=64 的 8.2%。

n=1024 的五次耗时从 3737.21 ms 到 3821.18 ms，极差约为中位数的 2.2%，小于 512→1024 的耗时倍数。

## 6. 分析

n 翻倍时，按上面的定义，乘加次数变成 8 倍。若每次乘加的平均耗时不变，耗时大约变成 8 倍，GFLOPS 大致持平。测到的耗时倍数是：

| 规模变化 | 运算量倍数 | 耗时倍数 | 耗时倍数 / 8 |
| --- | ---: | ---: | ---: |
| 64 → 128 | 8 | 16.986855 | 2.12 |
| 128 → 256 | 8 | 10.452699 | 1.31 |
| 256 → 512 | 8 | 7.801689 | 0.98 |
| 512 → 1024 | 8 | 35.998978 | 4.50 |

最后一列就是 GFLOPS 下降的倍数。n=512 的 2.561158 除以 n=1024 的 0.569162，同样约为 4.50。

1. 耗时与 n³ 的比例随规模变化。GFLOPS 从 n=64 的 6.93 降到 n=1024 的 0.569。
2. 256 → 512 的耗时倍数是 7.80，接近 8，GFLOPS 从 2.498 到 2.561。落差集中在 512 → 1024。
3. 按第 4 节的读法，n=64 的三个矩阵共 48 KiB，与每核 L1d 同一量级；n=128 和 n=256 落在每核 2 MiB 的 L2 内；n=512 的 3 MiB 超过每核 L2，耗时倍数仍接近 8；n=1024 的 12 MiB 仍在 320 MiB 的 L3 内。因此这次 GFLOPS 下降发生在 L3 容量之内。工作集超过某一级缓存，也不对应每一次耗时偏离：256 → 512 的耗时倍数仍接近 8。

内层沿 k 前进时，B 的地址跨步是 `n` 个 `int`：n=64 为 256 字节，n=1024 为 4096 字节。跨步变大后，同样次数的访问更难落在同一缓存行。

**假设：** 512 → 1024 的效率下降与 B 的跨步有关。若页大小为 4 KiB，n=1024 的跨步等于一页，可能增加 TLB 访问。本次记录没有页大小，也没有 cache-miss 或 dTLB-miss。下一步在同一口径下采集这些计数，或与循环重排的结果对照。

本次 GFLOPS 按整数乘加折算。编译选项是 `-O2`，报告不把它和机器的浮点峰值相除。
