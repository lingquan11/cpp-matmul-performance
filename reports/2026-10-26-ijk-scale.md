# 我的实验记录：i-j-k 从 64 测到 1024

2026-10-26。我是东南大学电子信息大一。数字都来自 [`results/2026-10-26_ijk-scale/`](../results/2026-10-26_ijk-scale/) 里的 `summary.csv` 和 `raw.csv`。

## 我想弄清楚的事

NPU 和 AI 芯片把很多面积花在乘加和搬数据上，因为模型里最重的就是矩阵乘法。朴素算法是三重循环，乘加次数是 Θ(n³)。次数我能算出来，数据来不来得及，我就得测。

这次我问的是：i-j-k 从 n=64 放到 n=1024，耗时会不会大约按运算量变成 8 倍，差别出在哪一档。

## 我测的是哪段循环

Day 1 的 `src/day01_matrix.cpp` 只算 C[0][0]。Day 2 的 `src/day02_matrix.cpp` 是固定 2×2 的 i-j-k，输出 `11 10` 和 `19 30`。基准里的 `benchmarks/kernels/ijk.cpp` 是同一套循环，上界换成 n。2026-10-26 记下来的源文件路径是 `benchmarks/ijk_kernel.cpp`，我现在把它放在 `benchmarks/kernels/ijk.cpp`。

```text
for i, for j:
  C[i][j] = 0
  for k: C[i][j] += A[i][k] * B[k][j]
```

A、B、C 我按行主序放。B 沿着 k 走，相邻两次差 n 个 `int`。循环重排、分块、脉动阵列和 SCALE-Sim 我写在最后。

## 我怎么计时

正式样本里只有实现函数被连续调用。构造输入、校准和正确性检查我放在计时外面。`ijk` 在函数里面把 C 写成 0，所以清零算进耗时。这是我 2026-10-25 定的口径。Day 3 笔记里我曾经想把清零放在计时外，那套和这套我分开看。

一次调用短于 100 ms 时，我在同一样本里连着重复。单次耗时 = 样本总耗时 / 重复次数。每个规模 5 个正式样本，表里用中位数，每一次的原始耗时在 `raw.csv`。

```text
GFLOPS = 2 * n^3 / 单次耗时（秒） / 1e9
```

这里的 2 是内层每一次做 1 次乘法和 1 次加法。内核是 32 位整数。我用 GFLOPS 比较同一次实验里的不同规模。

正确性我查了这些：Day 2 原程序输出 `11 10` 和 `19 30`；参数化之后的 `ijk` 在单位矩阵、零矩阵、全 1 矩阵和 n=3 上跟逐项乘加一致。同一个规模的 5 个样本，校验和相同。

## 机器和编译

原文在 [`environment.txt`](../results/2026-10-26_ijk-scale/environment.txt)，测量时刻 2026-10-26T04:05:29Z。

机器是 KVM 云端 VM，Ubuntu 24.04.5 LTS，Linux 6.12.94+。`lscpu` 的型号是 Intel(R) Xeon(R) Processor，family 6，model 207，stepping 2，4 vCPU。这台机器没有 cpufreq，所以我写不出标称频率。缓存按 `lscpu` 原文是 L1d 192 KiB（4 instances），L1i 128 KiB（4 instances），L2 8 MiB（4 instances），L3 320 MiB（1 instance）。MemTotal 是 16387280 kB。编译器是 g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0。当时的编译命令是：

```text
g++ -O2 -std=c++17 -Wall -Wextra -Werror -o build/matmul_bench benchmarks/matmul_bench.cpp benchmarks/ijk_kernel.cpp
```

这次表用的就是上面这条，优化级别是 `-O2`。我现在跑 `python3 benchmarks/run_bench.py` 时另外加了 `-falign-loops=32`，想让各内核的循环落在同样的对齐上。同一天我在这台 VM 上用两份相同循环对照过：n=64、各 2 个样本，不对齐大约是 3.87 和 6.94 GFLOPS，加上这个选项后大约是 6.84 和 6.85。上表的 i-j-k 大约 6.93，和较快的那一档接近。两套编译选项不一样，绝对值我分开比。

`lscpu` 写着 4 instances。我按每核一份来读：每核 L1d 48 KiB，每核 L2 2 MiB，L3 320 MiB 大家共用。这是我对字段的读法。

三个 `int` 矩阵我按 4 字节估算。x86-64 上 g++ 的 `int` 是 4 字节，结果文件里我没有单独打印 `sizeof(int)`。

| n | 三个矩阵一共 | B 的 k 方向跨步 |
| ---: | ---: | ---: |
| 64 | 48 KiB | 256 B |
| 128 | 192 KiB | 512 B |
| 256 | 768 KiB | 1 KiB |
| 512 | 3 MiB | 2 KiB |
| 1024 | 12 MiB | 4 KiB |

12 MiB 比记录里的 320 MiB L3 小。

n=1024 的 GFLOPS 是 0.569162。n=64 的 6.929414 大约是它的 12.17 倍（6.929414 / 0.569162），也就是 n=1024 大约是 n=64 的 8.2%。

n=1024 五次从 3737.21 ms 到 3821.18 ms，极差大约是中位数的 2.2%，比 512 到 1024 的耗时倍数小。

## 我注意到的地方

n 翻倍时，按上面的算法，乘加次数变成 8 倍。如果每次乘加的平均耗时不变，耗时也大约变成 8 倍，GFLOPS 会差不多持平。我测到的倍数是：

| 规模变化 | 运算量倍数 | 耗时倍数 | 耗时倍数 / 8 |
| --- | ---: | ---: | ---: |
| 64 到 128 | 8 | 16.986855 | 2.12 |
| 128 到 256 | 8 | 10.452699 | 1.31 |
| 256 到 512 | 8 | 7.801689 | 0.98 |
| 512 到 1024 | 8 | 35.998978 | 4.50 |

最后一列就是 GFLOPS 掉下去的倍数。n=512 的 2.561158 除以 n=1024 的 0.569162，同样大约是 4.50。

耗时和 n³ 的比例是随规模变的。GFLOPS 从 n=64 的 6.93 降到 n=1024 的 0.569。256 到 512 的耗时倍数是 7.80，接近 8，GFLOPS 从 2.498 到 2.561。掉得厉害的是 512 到 1024。

按上面的读法，n=64 三个矩阵一共 48 KiB，和每核 L1d 差不多；n=128 和 n=256 还在每核 2 MiB 的 L2 里；n=512 的 3 MiB 已经超过每核 L2，耗时倍数却还接近 8；n=1024 的 12 MiB 仍在 320 MiB 的 L3 里面。所以这次 GFLOPS 下降发生在 L3 还装得下的时候。工作集超过某一级缓存，也不等于每一档都会明显变慢：256 到 512 的耗时倍数仍然接近 8。

内层沿 k 走的时候，B 的地址跨步是 n 个 `int`。n=64 是 256 字节，n=1024 是 4096 字节。跨步变大以后，同样次数的访问更不容易落在同一条缓存行里。

我把下面这件事记成假设：512 到 1024 的效率下降和 B 的跨步有关。如果页大小是 4 KiB，n=1024 的跨步刚好一页，TLB 可能会更忙。我这次没记下页大小，也没采 cache miss 或 dTLB miss。下一步我打算在同一口径下把这些计数采下来，或者和循环重排的结果对着看。

这次 GFLOPS 是按整数乘加折算的。编译选项是 `-O2`，我不拿它去除以机器的浮点峰值。

进程我没有绑核。n=64 一次调用大约 0.076 ms，正式样本是 1322 次调用的平均，换算写在计时那一节。
